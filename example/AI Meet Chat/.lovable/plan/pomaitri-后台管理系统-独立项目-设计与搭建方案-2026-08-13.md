# POMaitri 后台管理系统（独立项目）设计与搭建方案

## 前提与边界

- 后台是**全新独立的 Lovable 项目**，独立仓库、独立部署、独立域名（如 `admin.*`）。
- 当前 Agent 产品（Web + iOS）**零改动**：不动 `src/routes/*`、`src/components/*`、`native/*`、样式与文案。
- 首版**只做后台骨架**：数据来自后台项目内部的 mock 适配器，不启用 Cloud、不建业务库、不接当前产品数据。
- 本项目内唯一新增文件：`docs/admin-console/spec.md`（后台需求与接口契约），供新项目落地时对照。

## 产品设计

### 角色与权限（细粒度权限点）

权限点采用 `资源:动作` 形式：

```text
users:read      users:write      users:ban       users:delete
stats:read      stats:export
invites:read    invites:write    invites:revoke
admins:read     admins:write     roles:write
audit:read
```

角色 = 权限点集合，可自由组合。内置三个预设角色（可编辑、可新增）：

- `super_admin`：全部权限点，唯一可管 `roles:write` / `admins:write`
- `ops`：users:read/write/ban + invites:* + stats:read
- `support`：users:read + stats:read（只读）

界面上，无权限的菜单项不渲染、无权限的按钮禁用并说明原因；服务端在每个接口再校验一次（首版为 mock 层的同构校验函数，接真库后原样搬到服务端中间件）。

### 页面结构

```text
/login                      后台登录（邮箱+密码，首版 mock）
/                           概览仪表盘
/users                      用户列表：搜索/筛选/分页
/users/:id                  用户详情：资料、心愿、匹配、连接、举报、操作
/stats                      数据统计
/invites                    邀请码：列表 / 批量生成 / 失效 / 使用追踪
/settings/admins            后台账号管理
/settings/roles             角色与权限点配置
/settings/audit             操作审计日志
```

### 各模块要点

**用户管理**：列表列（头像、名称、城市、注册时间、最近活跃、心愿数、连接数、状态）；筛选（状态、城市、注册时间段、是否完成资料）；详情页做操作：封禁/解封（必填原因）、重置资料可见性、删除账号（二次确认 + 输入用户名）。所有写操作写入审计日志。

**数据统计**：概览卡（总用户、今日新增、7 日活跃、心愿总数、匹配成功数、匹配成功率、邀请码使用率）；趋势图（注册、心愿发布、匹配成交，按日/周切换）；分布图（城市、运动类别、时间档位）；支持 CSV 导出（受 `stats:export` 控制）。

**邀请码管理**：批量生成（数量、备注、有效期、归属人）；列表显示码、创建人、状态（未用/已用/已失效/过期）、使用者、时间；操作为复制、批量导出、失效。

**后台账号与权限**：邀请后台成员（邮箱 + 角色）、停用账号、强制下线；角色编辑页用权限点复选矩阵；`super_admin` 不可被自己降权或删除（防锁死）。

**审计日志**：记录 who / when / action / target / 原因 / 结果，只读、可按操作人与资源筛选。

## 技术方案

新项目使用与当前一致的栈（TanStack Start + Tailwind v4 + shadcn），便于后续复用与维护，但**代码完全独立**。

```text
src/routes/                 页面（_authenticated 网关内为后台内页）
src/features/users|stats|invites|admins|roles|audit/
src/data/ports/             全异步接口 + 领域类型（后台侧契约）
src/data/adapters/mock/     首版实现：内存 + 固定种子数据
src/data/adapters/remote/   下一版：createServerFn / 真实库
src/data/index.ts           单一装配点（一行切换适配器）
src/auth/                   会话、权限点判定 hooks：useCan("users:ban")
```

关键约定：

- 与当前项目相同的分层纪律：页面只用 hooks，不直接触碰数据实现，端口方法全部 `Promise`。
- 权限判定实现两份同构调用：UI 层 `useCan()`，数据层 `assertCan()`。首版 `assertCan` 在 mock 适配器里执行；接真库后搬到服务端中间件，页面不改。
- 分页、排序、筛选参数从第一版就进端口签名（`{ page, pageSize, sort, filters }`），避免接真实接口时改所有调用点。
- 种子数据放 `adapters/mock/seed/`，接真库时整目录删除。

## 与当前 Agent 产品的对接（下一版，本次不做）

后台不直接读当前产品的浏览器本地存储。对接路径：当前产品启用 Cloud 后，后台通过共享的同一后端读数据 —— 后台的 `remote` 适配器落地，当前产品把 `src/data/index.ts` 从 `local` 切到 `remote`。两侧页面与交互均不改。

本次交付的 `docs/admin-console/spec.md` 会写明后台所需的表与字段（users / profiles / intents / matches / connections / invites / reports + admin_users / admin_roles / admin_role_permissions / audit_logs），作为将来建库的依据。

## 交付物

1. 本项目：新增 `docs/admin-console/spec.md`（权限点清单、页面清单、端口签名、数据字段契约）。业务代码零改动。
2. 新建独立项目 Maitri Admin：上述页面与模块全部可点可用，数据走 mock 适配器，权限点真实生效，含登录、概览、用户、统计、邀请码、后台账号/角色、审计七块。

## 验证

- 当前项目：`lint` / `build:dev` / 30 项单测 / e2e / 原生隔离校验全部与改动前一致（未触碰 `src/`）。
- 新项目：以三种角色分别登录，验证菜单可见性、按钮禁用、越权调用被 `assertCan` 拒绝；所有写操作产生审计记录。
